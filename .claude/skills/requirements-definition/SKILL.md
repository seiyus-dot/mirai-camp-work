# requirements-definition

MIRAI CAMP 7章で、タスク管理Webアプリの「何を作るか」「何ができれば完成か」を決めるための Skill です。
答えを決めるのは受講生です。この Skill は、たたき台を出して、質問と整理を手伝います。

## 読むファイル

- `README.md`
- `CLAUDE.md`
- `docs/templates/requirements-template.md`（要件定義書のひな形。見出しの順番はこれに従う）
- `.claude/skills/requirements-definition/examples/requirements.md`（完成見本：md）
- `.claude/skills/requirements-definition/examples/requirements.html`（完成見本：HTML。デザインとMermaidの読み込み方はこれをそのまま使う）

## 作るファイル

| ファイル | 役割 |
|---|---|
| `docs/requirements.md` | 要件定義書の**元の文書**。内容はこちらが正しい |
| `docs/requirements.html` | 図（Mermaid）と表が見やすく表示される**見る用のページ**。md と同じ内容にする |

すでにある場合は、追記するか作り直すかを受講生に確認してから進める。

## 変更してはいけないもの

- 上の2つ以外のすべてのファイル
- **アプリのコード**。この段階では実装しない（コードを書かない・変更しない・パッケージを入れない）
- `docs/templates/` のひな形と、この Skill の `examples/`（読むだけ）
- 追加のツールのインストールは行わない

## 進め方

### 1. 作業の説明

読むファイル・作るファイル・変更しないもの（特に「まだ実装しない」こと）を、初心者向けの言葉で説明する。

### 2. 進め方を選んでもらう

**文章で聞かず、選択画面（`AskUserQuestion`）で聞く。** 選択肢は次の2つ。最初の選択肢を「たたき台から進める（おすすめ）」にする。

1. **たたき台から進める（標準）**：完成見本と同じ6ページ版のたたき台を出し、受講生は「OK」か「ここを変えたい」と答える
2. **1問ずつ質問に答えて決める**：下の「質問の順番」で一問ずつ聞き、答えをもとに書く

- 受講生が「どっちでもいい」「任せる」と答えたら、1（たたき台）で進める。そのことを一言伝える
- 「すぐ作りたい」と言われた場合も、要件定義を飛ばすと何が起きるか（作ったあとで「欲しかったものと違う」となりやすい、完成の基準がなくなる等）を伝え、1 を提案する

### 3. たたき台を出す

- まず会話の中にマークダウンでたたき台を見せる
- 受講生が「ファイルで見たい」と言ったら、`docs/requirements.md` に**下書きとして**保存する。先頭に `> 下書き：受講生の確認待ち（OKが出たらこの行を消す）` を入れ、HTML にも同じ意味の表示を入れる
- `docs/` の外（一時フォルダなど）には書かない。フックに止められるため

### 4. 受講生の修正を反映する

- **修正のやり取りは、最大3往復まで**にする。授業の時間内に終えるため。3往復で決まらないことは、無理に決めず「未決定事項」に残して先へ進む（残したことは、報告のときに受講生へ伝える）
- 今が何往復目かを、毎回の返事の最初に一言で伝える（例：「修正 1/3」）
- 受講生の回答を**勝手に補わない**。足りないところは確認の質問をする
- 迷っていたら具体例や選択肢を出してよいが、採用するかは受講生が決める。おすすめがあれば理由を添えて1つ示す
- 決まらなかったことは推測で埋めず、**「未決定事項」にそのまま残す**
- 受講生と合意していないのに Claude が足した内容（例：初期値、移動のルール）は、報告のときに「私からの提案」と明示する
- 内容を変えたら、**md と HTML の両方を必ず同じ内容にそろえる**

### 5. 表示を確かめる

HTML を保存したら、ブラウザで開いて自分で確かめてから報告する。

- 2つの Mermaid 図（ページ構造・データ）が、文字のままでなく図になっている
- 表の列の幅や、ページ階層の一覧の位置がずれていない
- 文字が途中で不自然に改行されていない

ずれていたら直して、もう一度確かめる。

### 6. 合意したら仕上げる

受講生から「OK」が出たら、md と HTML の両方から下書きの表示を消す。

## 質問の順番（「1問ずつ」を選んだときの目安）

1. このアプリを主に使う人は誰か
2. その人の一番大きな困りごとは何か
3. アプリでどう解決するか
4. 必須機能は何か
5. 今回は作らないものは何か
6. どのページがあり、利用者はどう移動するか
7. どの情報を保存し、それらはどうつながるか
8. 何ができれば完成と言えるか（実際の操作で確かめられる言葉で）

質問は**一度に並べず、一問ずつ**する。答えを受けてから次に進む。

**質問の見出しに、進み具合を入れる**（例：「質問 3/8　アプリでどう解決しますか？」）。受講生が、あと何問で終わるか分かるようにする。1問あたりのやり取りは1〜2往復までにし、答えに迷ったら具体例や選択肢を出す（採用は受講生が決める）。

## 要件定義書の形

`docs/templates/requirements-template.md` の見出しを、順番どおりにすべて使う。見出し（`##`）は足さない・減らさない。見出しの中で小分けにしたいときは、太字の見出し（`**users（利用者）テーブル**` など）を使う。

完成見本（`examples/`）と同じく、各見出しは次の形で書く。

| 見出し | 書き方 |
|---|---|
| 必須機能 | 「Day1 の必須機能（講座の前提）」1〜6と「追加する機能」7〜に分け、番号を通しで付ける |
| 今回は作らないもの | 箇条書き |
| ページ構造 | ①ページの表（ページ・URL・できること） ②ページ階層の一覧（`text` のコードブロック） ③Mermaid の `flowchart TD`（矢印に「ログインする」などの操作名） ④移動のルール（未ログイン時の扱いなど）の箇条書き |
| データアーキテクチャ | ①Mermaid の `erDiagram`（型・PK・FK・日本語の説明つき） ②テーブル定義表（カラム名・型・必須・キー・説明）をテーブルごとに ③用語メモ（主キー・外部キー・型） ④つながり方の箇条書き |
| 扱う情報 | 情報・項目の表 |
| 完了条件 | 「Day1 の必須機能」と「追加する機能」に分けたチェックボックス（`- [ ]`）。実際の操作で確かめられる言葉で書く |
| 未決定事項 | 箇条書き。推測で埋めない |

### たたき台の初期値（6ページ版）

受講生と合意した場合に書く。違う答えが出たら、その答えを優先し、初期値と違う点を伝えて確認する。

- **必須機能**
  - Day1：ログイン、ログアウト、タスクの追加、一覧表示、完了、削除
  - 追加：タスクの編集（内容・メモ・期限）、完了済みタスクの一覧表示、表示名の変更
- **今回は作らないもの**：会員登録・パスワード再発行、複数人で一つのリストを共有、通知・リマインダー、カテゴリー分け・検索
- **ページ構造**

  | ページ | URL |
  |---|---|
  | トップページ（画面なし。ログイン状態で自動移動） | `/` |
  | ログインページ | `/login` |
  | タスク一覧ページ（未完了のタスク） | `/tasks` |
  | 完了済みタスクページ | `/tasks/done` |
  | タスク詳細ページ（編集・削除） | `/tasks/[id]` |
  | 設定ページ（表示名の変更・ログアウト） | `/settings` |

- **データアーキテクチャ**
  - `users`：`id`（uuid・主キー）、`email`（text）、`display_name`（text・空でもよい）
  - `tasks`：`id`（uuid・主キー）、`user_id`（uuid・外部キー → `users.id`）、`title`（text）、`memo`（text・空でもよい）、`due_date`（date・空でもよい）、`is_done`（boolean・最初は false）、`created_at`（timestamptz）
  - 利用者とタスクを `user_id` で関連づけ、ログイン中の利用者は自分のタスクだけを扱う
  - **SQL（データベースへの命令文）は書かない**。SQL は「データ保存」の段階で書く。受講生に SQL を求められたら、この理由を伝え、テーブル定義表で表す案を出す
- **未決定事項の例**：アプリの表示名、利用者アカウントの用意のしかた、完了済みを未完了に戻せるか、表示名の表示場所、期限切れを目立たせるか

受講生が「Day1 の2ページだけにしたい」と言ったら、トップ・完了済み・詳細・設定のページと、追加機能・追加カラム（`display_name`・`memo`・`due_date`）を外す。その場合、完了したタスクは一覧の中で完了したと分かる表示にする。

## HTML の作り方

- `examples/requirements.html` の `<head>`（スタイル）と、最後の Mermaid 読み込み `<script type="module">` を**そのまま使う**
- Mermaid は `https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs` から読み込む。インターネットにつながっていないと図が文字のまま表示されることを、受講生に伝える
- 中身は md と同じ順番・同じ文言にする。図は `<pre class="mermaid">` に md と同じ Mermaid の文字を入れる
- ページ階層の一覧は、罫線の文字の幅がずれるので `<pre>` ではなく、見本と同じ `<div class="tree">`（2列の並び）で書く
- 先頭の HTML コメントに「元の内容は docs/requirements.md」と書く

## 最後に

1. 保存した2つのファイルの場所を伝え、受講生が自分で開いて次の点を確認するよう促す
   - 必須機能にログインとログアウトが含まれているか
   - ページの表と図で、ページどうしの移動が分かるか
   - 利用者とタスクが `user_id` でつながっているか（ER 図とテーブル定義表）
   - 今回は作らないものが書かれているか
   - 完成を実際の操作で確認できる言葉になっているか
2. Mermaid の図をその場で見たいと言われたら、図にして会話の中に表示してよい（ファイルは増やさない）
3. 要件はあとから変えてもよい。ただし、変えたら会話だけで終わらせず、**md と HTML の両方**に反映するよう伝える
